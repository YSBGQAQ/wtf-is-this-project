# 项目速览骨架删去 Common questions 段

Matt Pocock 的 25 篇文章全部包含 `Common questions` 段，无一例外。我们研究他的格式规范，却在自己的骨架里删掉了这一段。

删它的理由：那段是 3–9 组问答，实测占全文近三成篇幅，对"一口气读完"是纯负担，与快原则冲突。而且它的一半内容是预答"你会不会想问 X"，属于交互引导——本 skill 已明确不做追问引导。

**连带处理**：他最有价值的两招——主动披露缺陷（给 issue 编号、标注未修、归因读者原话）与主动劝退（"On a one-day build, skip it."）——原本主要藏在这段里。砍掉后并入末段「它的边界在哪」，那里本就讲"它不做什么、什么时候不该用它"，语义吻合，不需要为它单开一段。

**代价**：读者当下的疑问不再被预答。这是有意为之，省下的篇幅让给"它解决什么问题"和"核心概念"两段的解释密度——对没写过代码的目标读者，这比预答疑问更有价值。

记录此决策是因为它是一次**主动偏离**：后人对照他的原文格式审视本项目时，会疑惑"为什么 25 篇都有、我们却没有"，很可能把它当成遗漏补回来。

## 修订：以简写形式回归

整段删除后，标杆样本暴露出两个问题——读者最可能被问到的三个疑问没有着落，且第 6 段被写成了功能清单而非生效信号。因此改为**保留该段，但压到 2–3 组、每组两行**。

原始担忧（占全文近三成篇幅）由"简写"化解：从 3–9 组长问答降到 2–3 组两行，篇幅不再是负担。

结论从"删掉"变为"压缩"。ADR 保留而非作废——它记录的是**为什么不能照搬**，这条理由依然成立。
