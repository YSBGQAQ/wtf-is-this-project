# Matt Pocock 文风规则

从 aihero.dev 的 25 篇 skills 系列文章中归纳而来，供 wtf-is-this-project 产出项目速览时使用。

本清单只管**内容与结构**。句法（AI 味、措辞）由《humanizer 中文句法清单》负责，两者不交叉。

## 方法说明

- 素材：`WEB.txt` 中的 **25 个 URL**（此前记为 24 个，`wc -l` 少计是因为文件末尾无换行符）。**25 篇全部抓取成功**。
- 分工：5 个子 agent 各负责 5 篇，逐篇精读并回报观察。
- 粗读的作用由**跨组比对**承担：某一组报的"共性"，必须在其余 4 组的报告中也得到印证，才升级为规则；只在 1–2 组出现的降级为个例，单独记录。
- 归纳式：未预设任何框架。子 agent 收到的指令只是"观察这些文章实际怎么写"，没有给它们要找的东西。

## 一、结构规范

### 1.1 他的骨架：25 篇无一例外

只用 H1 + H2，**全系列没有用过一次 H3**。

H1 之后、首个 H2 之前，还有一个**不带标题的前言区块**（5 部分 agent 最初误判为站点模板，已修正为正文结构）：

```
Install this skill           安装命令（一行 shell）
Then type `/X` in your       使用说明（一句直给）
coding agent.
───
Source                       源仓库链接
```

随后才进入七段同序的正文：

```
What it does          它做什么
When to reach for it  什么时候用
Prerequisites         前置条件        ← 只在约半数文章出现
〔1–3 个本篇专属节〕                  ← 名称各异，从不重复
Common questions      常见问题
It's working if       怎样算跑通了
Where it fits         它处在哪
```

每段的固定特征：

| 段 | 硬特征 |
|---|---|
| What it does | 第一句 = 反引号的 skill 名 + 动词，直给定义，零铺垫 |
| When to reach for it | 首句是逐字模板：`You invoke this by typing \`/X\`; the agent won't reach for it on its own.`；第二段常接"什么情况下该找它"，并配一张对照表 |
| It's working if | **每条都是可当场观察验证的行为**，不是原则。例：`It starts writing rather than asking you a fresh round of questions.` / `No code changed during the run.` |
| Common questions | 加粗问句（读者口吻）+ 回答，3–9 组 |
| Where it fits | 末节，路由说明，末句指向下一个 skill |

### 1.2 第二段必须划边界

这是全系列最稳定的规律，25 篇里绝大多数遵守。第一段给定义，**第二段立刻说它不是什么**：

> `codebase-design`: "It is a reference, not a process. There is no loop to run, no artifact it produces, no checkpoint where it asks you a question."
> `diagnosing-bugs`: "It never changes the code."
> `to-questionnaire`: "It grills you about the **send**, never the subject."
> `prototype`: "Throwaway is a constraint on how the code is *written*, not a promise to destroy it."

**先定义，再立刻划边界，比多写三段说明更有效。**

### 1.3 项目速览的骨架（由 1.1 映射而来，**两处重排**）

目标读者是"没写过代码的人"，比他的读者门槛低。段名从技术视角换成了读者视角的问题。

最终形态：**六段 + 一个文末问答区**。

| # | 段名 | 对应他的 |
|---|---|---|
| 1 | **怎么装上、怎么用** | 前言区块（Install + Then type）+ Prerequisites |
| 2 | **它解决什么问题** | What it does |
| 3 | **你什么时候会用到它** | When to reach for it |
| 4 | **核心概念** | 专属中段 |
| 5 | **装好之后你能做到什么** | It's working if |
| 6 | **它的边界在哪** | Where it fits |
| 末 | **你可能还会问** | Common questions + 未展开的细节 |

**两处重排，理由相同：让小白最关心的排在最前，把可问可不问的推到最后。**

1. **安装使用提到首位，并吃掉 `Prerequisites`。** 他把 Install / Then type 放在 H1 之后、正文之前的无标题区块里，各占一行；我们把它升为正经的第一段并扩写——这是纯小白唯一需要照着动手的部分，值得占篇幅。`Prerequisites` 并进来，因为它本质上就是"装之前要准备什么"，单独成段会打断"怎么上手"的连贯性。
2. **问答区合并并下移到文末。** `Common questions` 从 3–9 组长问答压到 2–3 组、每组两行，再并入"没展开的几件事"。两者都是"读者可能想问、但不必现在展开"的内容，分开放会两次打断阅读，合并成一处搁在最后。

**第一段内部仍是他的老规矩**：第一句「项目名 + 动词」给定义，第二句立刻划边界，然后才进安装步骤。读者先花十秒知道自己在装什么，再看怎么装。

**一处内涵要校准**：第 5 段对应 `It's working if`，写的是**生效信号**——"读者怎么知道它起作用了"，不是功能清单。

**N4 的归属**：纠正认知偏差（N4）与主动劝退（N5）都落在第 6 段，不在问答区。

## 二、文风规则（S 结构 / W 写法 / T 术语 / N 不说）

### S 组：结构

- **S1** 第一段的第一句必须是「项目名 + 动词」给定义，第二句立刻划边界，然后才进安装步骤。不许有"在本文中""你有没有遇到过"这类开头。
- **S2** 第一段的第二句必须划边界：它不做什么。用"X，不是 Y"句式。
- **S3** 只用两级标题。不给标题分级到第三层。
- **S4** 固定六段 + 一个文末问答区，顺序不可换。缺内容就整段省略，不要重排。问答区压到 2–3 组，末尾另附未展开细节清单。
- **S5** 「装好之后你能做到什么」写的是**生效信号**：读者怎么知道它起作用了。不是功能清单。
- **S6** 结尾不总结、不复述、不喊口号，落在边界上。纠正认知（N4）与主动劝退（N5）一并放在末段。

### W 组：写法

- **W1** 第二人称"你"讲读者，第三人称"它"讲项目。作者不以"我"出场——"我"只出现在引用别人原话时。
- **W2** 陈述句为主。祈使句只在给指令时出现，短而直给。
- **W3** 句长两极：3–8 字的短句单独成句，用来落断言；长句承担定义与限定。不要全是中长句。
  > 例：`No.` / `Yes, and plenty of people did before it existed:` / `That is the whole skill.`
- **W4** **"X，不是 Y" 是招牌句式**，每个概念定义都要用它。这是全系列密度最高的句式。
  > 例：`shorter and clearer, not shorter and blunter` / `A quiz is a gate, not a formality` / `an index, not a store`
- **W5** "没有 X" 用来干脆地否定不存在的事：`There is no alias.` / `There is no fix shipped yet.`
- **W6** 问答先抛结论再展开，一句话开头：`Not as a step of its own.` / `No, and a cap is deliberately out of scope.`
- **W7** 段落用短判断句收束：`Nothing needs to exist before you start.`

### T 组：术语

- **T1** 四件套：**命名 → 定义 → 可执行判据 → 避免用词**。他的词汇表就是这个形状：
  > `Interface` — "Everything a caller must know to use it correctly: the type signature, plus invariants, ordering constraints, error modes" — _Avoid_: API, signature
- **T2** **给判据，不给形容词**。判据要能当场执行：
  > `deletion test`: "Imagine deleting the module. If complexity vanishes, it was a pass-through."
  > "One adapter means a hypothetical seam. Two adapters means a real one."
- **T3** 命名后立刻白话重述；概念抽象时给比喻。
  > "an interface nearly as complex as the thing it hides"（解释 shallow）
  > "An agent that hears 'be brief' writes telegrams."
- **T4** 变体：先给场景，再落地术语。
  > "'One long form or three pages?' and 'how should this interaction feel?' are **ungrillable**: they need something to react to."
- **T5** 术语注释必须让**去掉注释后句子仍然自足**。他的做法是术语外链到词典、去掉链接句子照样读得通；中文对应做法就是括号注释，且括号里的东西删掉不影响主干。

### N 组：不写什么

- **N1** 不开篇导语，不写背景铺垫，不解释"为什么需要这个"。
- **N2** 不写总结段、Key takeaways、行动号召。最后一段是"它的边界在哪"，不是回顾。
- **N3** 不用营销形容词。他全系列没出现过 powerful / seamless / effortless。
- **N4** **纠正会误导读者的认知，但不罗列工程状态。** 这是对原始做法的**收窄**——他的读者是工程师，我们的读者是没写过代码的人。

  | 要写 | 不写 |
  |---|---|
  | 会让人理解错的口径（"省 90%" 其实是省 bash 输出字节，不是省账单） | 未关闭 issue 数、bug 清单 |
  | 适用范围（认得的命令才压，其余原样通过） | 版本漂移、安装文档过时 |
  | 失效方式（压缩没生效也不报错） | 文档自相矛盾、社区争议 |

  判据：读者看完**能不能据此做决定**。能，就写；只是让他知道"这个项目挺乱"，就不写。
  写法：一句话纠正，不引用英文原文，不比较哪份文档说得对。
- **N5** **该劝退就劝退**，且用"honest"这类词直接限定自己。**同样写进末段**：
  > "On a one-day build, skip it."
  > "the honest answer is that you don't need this."
  > "the honest map is that you'll use it less often than the other four options"
  > 路由表末行直接写 `Nothing here fits well`
- **N6** 无客套、无免责声明、不安抚读者。
- **N7** 不放安装步骤、截图、价格、竞品对比、作者自述动机。

## 三、篇幅观察

25 篇英文正文的实测范围：**约 600 词至 2300 词**（多数落在 1100–1900 词）。最短的是 `wait-what`（~600）、`resolving-merge-conflicts`（~600），最长的是 `teach`、`code-review`、`prototype`（~1900–2300）。

**这不是我们要照搬的数字。** 他的读者是工程师，我们的读者是没写过代码的人——单点解释成本更高，但整体深度要更浅。按快原则取短端，具体长度仍由内容决定，不设硬指标。

## 四、反例与例外

以下文章不遵守上述部分规律，如实记录，避免把个例当共性：

| 文章 | 偏离 |
|---|---|
| `wait-what` | 违反最多：无 Common questions、无对照表、无缺陷披露、篇幅约为 `teach` 的三分之一。它是唯一几乎纯讲机制的。 |
| `resolving-merge-conflicts` | 篇幅最短档，只有 1 个中段节，缺陷披露强度明显弱于其他篇。 |
| `writing-for-agents` | 全篇无表格（其余篇目普遍用表格承载信息）。 |
| `grill-me` | 唯一把 Common questions 放在 It's working if **之后**的。 |
| `setup-matt-pocock-skills` | 唯一引用用户原话（"hard locked to github"、"Config is death."），并把"这 skill 该不该存在"的反对意见写进 Common questions。 |
| `to-spec` | 全系列表格最少（仅 1 张），是"表格个例"。 |
| `tdd` | 结尾多一行页脚标语，其余篇目无。 |

**共性强度分级**：

- **25 篇无例外**：七段骨架、只用 H2、第二段划边界、第二人称叙事、作者不以"我"出场、It's working if 为可观察行为清单。
- **约 4/5**：缺陷披露并归因给读者、`Where it fits` 末句路由到 ask-matt、`When to reach for it` 配对照表。
- **约 3/5**：`Prerequisites` 段存在、副标题与署名存在。
