# wtf-is-this-project

`wtf-is-this-project` 把一个陌生的源项目变成一份**项目速览**。它动的是**理解**，不是翻译——把 README 复述一遍不算数。

读者设定为没写过代码的人："仓库""命令行""依赖"要解释，"变量""文件"不用解释。

## 输出形态

**直接呈现在对话里，不是落盘文件。** 这份速览的归宿是你和提问者之间的对话——提问者滚动屏幕就能读，不需要打开任何附件。**Skill 不创建 `.html`、`.md`、`.pdf` 或任何其他文件**。源项目本身可能是一份 markdown 或代码仓库，但产出的形态始终是一段对话消息。

## 开工前先读这三份

不读完不许动笔。它们定义了"好"是什么：

| 文件 | 管什么 |
|---|---|
| `references/文风规则.md` | 内容与结构：六段骨架，S/W/T/N 四组规则 |
| `references/中文句法清单.md` | 句法：中文 AI 味检查表，分 A/B/C/D 四组 |
| `references/标杆样本.md` | 一份人类认可的完整样本，照它的密度和口气写 |

文风规则管内容与结构，句法清单管句子措辞。两者不交叉。

## 排版约定 — GPT 式排版

按 GPT / ChatGPT 习惯的格式写。靠**视觉锚点 + 短句 + 编号**让读者一眼能扫。

### 四个原则

(1) **标题必须用 Markdown 语法**：`#` 是文档唯一主标题，`##` 给六个正文段。聊天窗口靠这个渲染出不同字号。**不要用 `**粗体**` 冒充标题**——粗体是行内样式，不产生字号层级，看上去会比真标题小一号。

(2) **小节锚点**：每个标题的文字前面放一个 emoji —— `🔥` `⚡` `📌` `🎯` `🛠` `🎨` 等。**emoji 是标题的前缀，不是标题本身**：写 `## 🔥 怎么装上、怎么用`，不写 `## 🔥`，也不写 `**🔥 怎么装上、怎么用**`。

(3) **短句 + 编号**：条目用 `1. 2. 3.` 编号，不用 Markdown 列表（避免多余缩进）。段内用短句，长句拆短。

(4) **视觉密度**：每个句子里最多一个粗体、一个 inline code、一个 emoji。多了就乱。

### 元素用法

| 元素 | 用途 |
|---|---|
| `🔥` `⚡` `📌` `🎯` `🛠` | 小节开头锚点 |
| `inline code` | 文件名、命令名、配置项、错误码、URL 路径段 |
| `**粗体**` | 一段话里的关键词（每段不超过 2-3 处） |
| `→` | "意思是" / "等价于" / 流程指向 |
| `❓` | 自问、引出下一段 |
| `✅` `❌` `⚠️` | 状态标记、对比 |
| `➡️` `⬇️` | 流程图节点之间 |
| `🟦` `🟪` `🟩` `🟥` | 流程图节点色块 |
| `😂` `🤔` `😅` | 偶尔的语气 emoji，整段不超过 1 个 |

### 严格禁用

- 缩进（不靠 Tab / 空格撑层级）
- **用 `**粗体**` 冒充标题** —— 字号会小一号，层级感全丢
- **只用 emoji 当标题**（如 `## 🔥` 后面不写文字）—— emoji 是前缀，不是标题本身
- ASCII 框图（`┌─┐│└┘`）与彩色 emoji 混用——这种组合在不同字体里字宽不一致，渲染必乱

### 表格、代码块、图表：保留原样

- **表格**：对比类内容（你什么时候会用到它、自检清单）直接用 Markdown 表格。
- **代码块**：放真正可执行命令、字符图、或可运行的代码片段时才用。
- **图表**：纯文字 + emoji 锚点 + 箭头，不依赖 Unicode 框图在特定字体的支持。

### 样板

下面这条展示了 GPT 式排版的典型形态。**注意标题是 `#` / `##`，emoji 只是前缀**：

~~~
# 🔥 【最接近「傻子也能看懂项目」】

## 📌 三个候选

1. `idiot-proof-github.skill` → "傻瓜都能用/看懂的 GitHub 项目"
   很地道，**idiot-proof** 本就是英语里的固定说法。
2. `github-for-absolute-idiots.skill` → "给彻头彻尾的傻瓜看的 GitHub"
   夸张程度很高，**非常符合你说的那个味道**。
~~~

## 第 1 步：探查提问者环境

产出之前，先弄清楚提问者在哪种环境下：

- **操作系统**：macOS / Windows / Linux。可从 `uname -a`、环境变量、文件路径或直接问一句判断。
- **已经在用的 AI 工具**：Claude Code / Cursor / Codex / Copilot / Gemini CLI 等。
- **可用的包管理器**：brew / apt / dnf / scoop / winget / chocolatey。
- **懂不懂命令行**：能跑命令就给命令；不能就直接给下载链接 + 图形说明。

环境不明的部分保留位「**用系统默认**」，不要瞎猜。

## 第 2 步：摄入

源项目可以是 GitHub 仓库、网页文章，或本地文本／目录。三种走**同一套产出结构**，只在"怎么读"这一步分叉。

**只读取，不 clone。** 不在本机留下第三方仓库。

按规模启用子 agent 并行处理：

(1) 源文件数 < 20：不用，直接读
(2) 20–100：3–4 个
(3) > 100 或多 package：6–8 个

**上限 8 个。** 再往上，汇总开销会吃掉并发带来的收益。

**快原则是第一原则**，优先级高于覆盖面。读不完就读主干；写不出来的段就整段省掉——骨架允许缺段，不允许凑数。

**特别说明**：纯小白速览需要的几乎所有信息都在 README、官网与文档里，**不在源码里**。派 8 个子 agent 去读 127 个 .rs 文件，既慢且大多用不上。源文件数与「实际要读的材料」并不成正比。

## 第 3 步：过一遍事实

这一节的目的只有一个：**少查**，不是多查。

(1) **需要复核才能拿到的数字，直接省略。** star 数、issue 数、版本号——这类数字要么花一轮去实测，要么冒着写错的风险抄，而读者拿着它们做不了任何决定。不问、不查、不写。
(2) **要写进正文的，回到原始来源看一眼。** 子 agent 报的不直接抄；文档里稳定写着的才用。不写的就不查。
(3) **非英文 README 可能过时。** 本地化文档常落后于英文原版，命令写法都可能已经变了。以英文原版为准。

## 第 4 步：写

骨架六段，顺序不可换。缺内容就整段省掉，不要重排。

1. **怎么装上、怎么用**（含装前准备）
2. **它解决什么问题**
3. **你什么时候会用到它**（用表格对照）
4. **核心概念**
5. **装好之后你能做到什么** —— 写**生效信号**：读者怎么知道怎么知道它起作用了。不是功能清单
6. **它的边界在哪**

H1 与第 1 段之间放一行源项目标注：`源项目 <地址> · 语言 · 许可`。

文末一个问答区：**2–3 组两行问答**，加一份**未展开细节清单**（一条一句话，只给入口不展开）。

**第一段内部的老规矩**：第一句「项目名 + 动词」给定义，第二句立刻划边界，然后才进安装步骤。

### "装它"必须给直接下载链接 ❗

**不要写"去官网下载"、"看官网"、"参见官网"这种甩手话。** 对小白来说那就是没讲。

(1) 项目有 **GitHub Releases**：调 API 拿当前版本与各平台安装包，**把对应系统的具体下载链接贴在文档里**。
(2) 平台官方有装（如 brew / winget / apt）：把命令直接写出来，按读者操作系统分支。
(3) 只能源码构建：给当前 OS 对应的命令，**不写"克隆后 npm install"这种命令糊脸**——补一句"如果你不熟命令行，最方便的办法是让熟悉的朋友帮一下"。

### "怎么用"对齐读者环境

探查阶段知道读者用的是哪个 AI 工具，就给出对应的具体步骤。**不要罗列所有工具**——只针对读者环境里有的那个。

篇幅由内容决定，说到清楚为止。不设字数上下限。

## 第 5 步：自检

逐条过，不过就改：

- [ ] 没写过代码的人读完，能说得出这项目解决什么问题
- [ ] 陌生术语全部带行内括号注释；去掉注释，句子仍然自足
- [ ] 正文没有裸代码片段，只留"一句话 + 文件名"的钩子
- [ ] 结构性 emoji 按角色使用，**同一份文档内同一 emoji 必须承担同一角色**
- [ ] 标题用 `#` / `##` 语法，**不是 `**粗体**`**；emoji 是标题前缀，不是标题本身
- [ ] 每个主要小节开头有一个 emoji 锚点（`🔥` `⚡` `📌` 等）
- [ ] 关键术语用 `inline code` 包裹；关键判断用 `**粗体**` 强调
- [ ] 流程 / 对比类内容用了纯文字 + emoji 锚点的图；没有 Unicode 框图与彩色 emoji 混用
- [ ] 「装它」段给了**直接下载链接或命令**，不是"去官网"
- [ ] 中文 AI 味清单自检：B 组命中 0
- [ ] 篇幅由内容决定，没为凑长度注水
- [ ] 没超过耗时基线（人工写一份同等质量的速览约 14 分钟）
- [ ] 产出是纯对话消息，未创建任何文件
- [ ] 整篇不缩进，**靠编号层级撑结构**

## 不做什么

- 不做多模态（视频、音频）
- 不产英文版
- **不创建任何文件** —— 所有产出都是对话消息
- 不给"你可能还想问"的交互引导
- 不追究底层实现：指出关键文件在哪可以，解释它内部怎么运作不行
- 不罗列工程状态：未关闭 issue 数、bug 清单、版本漂移、文档自相矛盾——纯小白无从据此行动
- **不查不稳定的数字**：star 数、issue 数、版本号
- 不粉饰：会让人理解错的口径要纠正，什么时候不该用要直说
- **不甩手**：不写"去官网""看官网""参见官网"——给直接下载链接
